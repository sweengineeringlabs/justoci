Results

Measured on Windows 11 x86-64, Criterion 0.5, 100 samples, 3 s warmup, release profile. Output written to tempfile::TempDir on NTFS. Source blob pre-written once and re-used; fresh output directory per iteration.

PayloadMean timeThroughput
4 KB17.6 ms227 KiB/s
1 MB19.5 ms51.3 MiB/s
16 MB71.7 ms223 MiB/s
The 4 KB and 1 MB cases take nearly identical time. Fixed overhead — not data processing — is the entire cost for small artifacts.

What is being measured

The timing window covers the complete oci_build::build() pipeline: spec to final OCI Layout directory, end-to-end with real disk I/O.

Layer data flows through 64 KiB chunks — no full-payload Vec<u8> is allocated inside the timing window. The source blob is pre-written once outside any iteration. The only per-iteration allocation is a fresh tempfile::TempDir.

b.iter_batched(
    || tempfile::TempDir::new().unwrap(),   // setup: fresh output dir
    |out_dir| build(&spec, out_dir.path()), // measured: full pipeline

Fixed overhead breakdown

The ~18 ms floor is five operations that happen regardless of payload size. At 4 KB, this is 100% of the cost. At 16 MB, it is ~25% of the cost.

TempDir::new()
~5 ms
CAS write (tmp → rename)
~6 ms
Manifest + config JSON
~1.5 ms
index.json + oci-layout
~1 ms
.partial → final rename
~1.5 ms
Data (16 MB, uncompressed)
~54 ms (proportional)

These are inherent to what justoci is: a tool that writes real files, atomic renames, and JSON manifests. Any tool in this space that assembles OCI layouts locally pays an equivalent floor — the exact split varies by implementation.

Throughput scaling

At 16 MB, data processing (~54 ms) overtakes the fixed overhead and throughput reaches ~223 MiB/s. This is NTFS write bandwidth for uncompressed application/octet-stream layers — the bottleneck shifts from metadata to disk I/O.

PayloadFixed overheadData costBottleneck
4 KB~17.6 ms (100%)<0.1 msMetadata ops
1 MB~17.6 ms (90%)~1.9 msMetadata ops
16 MB~18 ms (25%)~54 msNTFS write bandwidth
Adding Gzip (level 6) or Zstd (level 3) compression reduces disk I/O at the cost of CPU — streaming encoders chain directly (file → encoder → CAS), no intermediate buffer. For bandwidth-constrained storage, compression increases effective throughput; for NVMe, uncompressed is usually faster.

Real use cases

Firmware images, ML model weights, and VM rootfs blobs are typically 10–500 MB. In that range justoci runs at 100–223 MiB/s.

ArtifactTypical sizeEstimated time
Embedded firmware2–20 MB60–120 ms
VM rootfs (microVM)20–100 MB120–500 ms
ML model (small)100–500 MB500 ms – 2.5 s
VM rootfs (full Linux)500 MB – 2 GB2.5 s – 10 s
For pipelines building many small artifacts (< 1 MB), the ~20 ms overhead per build dominates. Batching small files into fewer, larger layers eliminates most of it.

vs oras

Measured via OrasRunner in the same Criterion harness — oras push --plain-http to a local registry:2 container over loopback, 100 samples, 3 s warmup, same payload sizes.

These numbers are not directly comparable. oras push transmits a blob to a registry over HTTP/loopback. justoci::build assembles an OCI layout to local disk with no network involved. justoci is the build step; oras is the push step. The comparison is order-of-magnitude orientation, not apples-to-apples.
Payloadjustoci (local disk)oras push (loopback)justoci advantage
4 KB14.1 ms132.5 ms9.4×
1 MB19.9 ms132.5 ms6.7×
16 MB74.7 ms167.1 ms2.2×

oras fixed overhead is ~130 ms — Go subprocess spawn plus an HTTP round-trip to a loopback registry. Both 4 KB and 1 MB take nearly identical time; only at 16 MB does data transfer start to matter. At 16 MB oras reaches ~96 MiB/s vs justoci's ~214 MiB/s on local NTFS.

The relevant distinction: justoci writes to local disk. A push to a remote registry always adds the network round-trip on top, regardless of which tool built the layout. The two operations are complementary, not competing — justoci builds, oras (or any push tool) ships.

Reproducing

Prerequisites

RequirementNotes
Rust stable toolchainrequired
Docker + oras 1.x (oras comparison only)docker run -d -p 5000:5000 registry:2

Steps

1. Clone and enter the workspace

git clone git@github.com:sweengineeringlabs/justoci.git
cd justoci

2. Run all cases (justoci only)

cargo bench -p swe_justoci_bench --bench build

3. Run with oras comparison

docker run -d -p 5000:5000 registry:2
cargo bench -p swe_justoci_bench --bench build --features justoci,oras

4. Run a single case

cargo bench -p swe_justoci_bench --bench build -- "build_oci_artifact/16mb"

Output

Criterion prints to stdout. An HTML report with plots is written to target/criterion/build_oci_artifact/report/index.html. This file is ephemeral — cargo clean removes it.
