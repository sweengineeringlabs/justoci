Fixed overhead breakdown

The ~14 ms floor for justoci is five operations that happen regardless of payload size. At 4 KB, this is 100% of the cost. At 16 MB, it is ~20% of the cost.

TempDir::new()
~5 ms
CAS write (tmp → rename)
~6 ms
Manifest + config JSON
~1.5 ms
index.json + oci-layout
~1 ms
.partial → final rename
~1.5 ms
Data (16 MB, uncompressed)
~58 ms (proportional)

These are inherent to what justoci is: a tool that writes real files, atomic renames, and JSON manifests. Any tool in this space that assembles OCI layouts locally pays an equivalent floor — the exact split varies by implementation.

Throughput scaling

At 16 MB, data processing (~58 ms) overtakes the fixed overhead and throughput reaches ~220 MiB/s. This is NTFS write bandwidth for uncompressed application/octet-stream layers — the bottleneck shifts from metadata to disk I/O.

PayloadFixed overheadData costBottleneck
4 KB~14.5 ms (100%)<0.1 msMetadata ops
1 MB~14.5 ms (82%)~3.2 msMetadata ops
16 MB~14.5 ms (20%)~58 msNTFS write bandwidth
Adding Gzip (level 6) or Zstd (level 3) compression reduces disk I/O at the cost of CPU — streaming encoders chain directly (file → encoder → CAS), no intermediate buffer. For bandwidth-constrained storage, compression increases effective throughput; for NVMe, uncompressed is usually faster.

Real use cases

Firmware images, ML model weights, and VM rootfs blobs are typically 10–500 MB. In that range justoci runs at 100–220 MiB/s; publish (loopback) at ~477 MiB/s for payloads that hit the data-transfer regime.

ArtifactTypical sizeEstimated time
Embedded firmware2–20 MB60–120 ms
VM rootfs (microVM)20–100 MB120–500 ms
ML model (small)100–500 MB500 ms – 2.5 s
VM rootfs (full Linux)500 MB – 2 GB2.5 s – 10 s
For pipelines building many small artifacts (< 1 MB), the ~14 ms justoci overhead per build dominates. Batching small files into fewer, larger layers eliminates most of it.

Three-way comparison: justoci vs publish vs oras

All three runners measured in the same Criterion harness — 100 samples, 3 s warmup, release profile. justoci writes to local NTFS. publish and oras push to a local registry:2 container over loopback.

These are different operations. justoci builds an OCI layout to local disk (no network). publish pushes in-process over loopback HTTP. oras invokes an external Go subprocess. They are not interchangeable — the comparison gives order-of-magnitude orientation for pipeline design, not apples-to-apples benchmarking.
Payloadjustoci (local disk)publish (in-process HTTP)oras (subprocess HTTP)
4 KB14.5 ms / 276 KiB/s39.0 ms / 103 KiB/s181.9 ms / 22 KiB/s
1 MB17.7 ms / 56.7 MiB/s33.4 ms / 29.9 MiB/s168.0 ms / 5.95 MiB/s
16 MB72.7 ms / 220 MiB/s33.6 ms / 477 MiB/s233.8 ms / 68.4 MiB/s

justoci vs oras: 12.5× / 9.5× / 3.2×

oras fixed overhead is ~170 ms — Go subprocess spawn plus the HTTP round-trip to a loopback registry. Both 4 KB and 1 MB are dominated by this floor. At 16 MB data transfer closes the gap slightly (oras reaches ~68 MiB/s), but justoci on NTFS stays 3.2× ahead.

publish vs oras: 4.7× / 5.0× / 7.0×

Eliminating the subprocess (~150 ms spawn overhead) and pushing in-process via oci_publish beats oras at every payload. At 16 MB the advantage grows: publish hits 477 MiB/s while oras caps at 68 MiB/s — the subprocess I/O path bottlenecks before the loopback link saturates.

The 16 MB crossover: publish beats justoci

At 16 MB, publish (33.6 ms / 477 MiB/s) is 2.2× faster than justoci (72.7 ms / 220 MiB/s). NTFS random-write with atomic rename overhead (~200–300 MB/s effective) loses to loopback TCP (~530 MB/s after blob dedup). For pipelines that push to a registry anyway, oci_publish skips the intermediate OCI layout write entirely.

The operations are complementary: build once to disk with justoci for offline/air-gapped use, push with publish when the registry is the destination. Or call publish directly and skip the disk step altogether at large payload sizes.

Reproducing

Prerequisites

RequirementNotes
Rust stable toolchainrequired
Docker (publish + oras runners)docker run -d -p 5000:5000 registry:2
oras 1.x on PATH (oras runner only)winget install ORASProject.ORAS

Steps

1. Clone and enter the workspace

git clone git@github.com:sweengineeringlabs/justoci.git
cd justoci

2. Run all cases (justoci only)

cargo bench -p swe_justoci_bench --bench build

3. Run the three-way comparison

docker run -d -p 5000:5000 registry:2
OCIMAGE_ALLOW_INSECURE=1 cargo bench -p swe_justoci_bench --bench build --features justoci,publish,oras

OCIMAGE_ALLOW_INSECURE=1 opts the publish runner into plain HTTP — required for a local registry:2.

4. Run a single case

cargo bench -p swe_justoci_bench --bench build -- "build_oci_artifact/16mb"

Output

Criterion prints to stdout. An HTML report with plots is written to target/criterion/build_oci_artifact/report/index.html. This file is ephemeral — cargo clean removes it.
